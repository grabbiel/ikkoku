# Character-card mod references

Character-card settings import preserves the card's original bytes and extended
data. The resolver adapter reads Sideloader's saved asset identities so an
imported card can be checked against the explicitly mounted native mod library.
Finding a matching catalog entry does not by itself render its mesh, material,
hair, clothes or accessory. Those assets still require native adapters.

Maker displays this report under **Card mod references** after importing source
card settings, and refreshes it when a library is loaded, reloaded or unloaded.
The CLI equivalent is `ikkoku-inspect card-mods <card.png> <library.json> <catalog-contract.json>`.
Each result retains its source record, actual destination, matching catalog row
and typed asset dependencies. Catalog lookup indexes exact GUID/category/source-slot
keys and evaluates only the dependencies of matched rows. Malformed resolver
metadata remains a visible diagnostic while valid shape settings can still import.

The independent source contract is generated by
`Tools/reverse/analysis/resolver_contract.py`. It reads the already recovered
local assemblies and decompiled source under ignored `.local`; it does not run
managed plugins. Generated cards contain synthetic fields and a blank one-pixel
PNG, not a user's character or a screenshot of the original game.

## Source wire format and precedence

ExtendedSaveFormat first selects the card's complete plugin dictionary. A valid
legacy `KKEx` version 2 footer replaces the current version 3 dictionary, as
described in [reverse-card.md](reverse-card.md). Within that selected dictionary,
UniversalAutoResolver chooses the first non-null plugin in this order:

1. `EC.Core.Sideloader.UniversalAutoResolver`
2. `com.bepis.sideloader.universalautoresolver`

The source does not check the selected plugin's version. A non-null EC plugin
without an `info` field suppresses the Koikatsu plugin; it does not cause a
fallback to the second ID. A null plugin entry permits fallback. A selected
plugin with null `data` makes the original hook fail when it accesses the
dictionary; the native adapter diagnoses malformed data instead.

`PluginData.data["info"]` is a MessagePack array of binary values. Each binary
value is a separate uncompressed MessagePack `ResolveInfo` object with string
map keys:

| Wire key | Type | Missing-field default | Meaning |
| --- | --- | --- | --- |
| `ModID` | String or nil | nil | Mod GUID; setter trims .NET whitespace |
| `Slot` | Int32 | 0 | Original catalog slot |
| `LocalSlot` | Int32 | 0 | Previous session's generated runtime slot |
| `Property` | String or nil | nil | Full destination path in the card |
| `CategoryNo` | Int32 | 0 | Category captured when saving the reference |
| `Author` | String or nil | nil | Optional missing-mod display metadata |
| `Website` | String or nil | nil | Optional missing-mod display metadata |
| `Name` | String or nil | nil | Optional missing-mod display metadata |

The original class formatter skips unknown string keys and gives the last
occurrence of a known key precedence. Every occurrence is still type checked,
so an earlier invalid value is not rescued by a later valid value. This differs
from an ordinary MessagePack dictionary, whose source formatter rejects
duplicate keys. Unknown data and duplicate wire fields remain in the retained
raw record even when they do not affect the interpreted value.

The GUID setter uses `String.Trim()`, which removes .NET whitespace characters
including nonbreaking and ideographic spaces. It does not remove zero-width
space or the byte-order-mark character. GUID and property comparisons are
case-sensitive and do not perform Unicode normalization.

## Binding to actual character destinations

The source enumerates real card fields and finds the **first** saved record whose
full `Property` exactly matches each destination. The emitted prefixes are:

| Destination | Full property example |
| --- | --- |
| Face, body, hair or base makeup | `ChaFileFace.Pupil1` |
| Card outfit clothing | `outfit0.ChaFileClothes...` |
| Card outfit accessory | `outfit0.accessory3.ChaFileAccessory.PartsInfo.id` |
| Standalone coordinate accessory | `accessory3.ChaFileAccessory.PartsInfo.id` |

The indexed suffixes come from the source structure mapping; they are not
inferred from user-visible catalog names. Coordinate makeup is not traversed by
the original `IterateCoordinatePrefixes` method.

For an explicit nonblank GUID, the exact lookup key consists of:

- the saved record's original `Slot`;
- the **current destination's category**, taken from the card structure;
- the unprefixed catalog property;
- the trimmed saved GUID.

The first matching catalog registration wins in source order. A native profile
provides its own explicit package order; it does not reproduce every original
archive discovery or version-selection decision automatically.

The saved `CategoryNo` is not used in this direct lookup. In particular, an
accessory destination's current `type` determines its category. A mismatching
saved category is useful diagnostic information, but treating it as the lookup
category would select the wrong asset or incorrectly report a missing mod.
`LocalSlot` is never a stable identity and must not be imported as a native
resource identifier.

When no matching marker exists, or the selected marker has a blank GUID, the
source falls back to its compatibility resolver. That path starts from the
actual card field's current slot, checks original base catalogs, then searches
loaded mod registrations and migrations. It does not use the saved record's
`Slot` or `LocalSlot` as a substitute for the original field. Unsupported
compatibility cases must remain diagnostic rather than be assigned a guessed
asset.

## Native destination scan

`SourceCharacterCard.resolverDestinations(contract:)` reads actual serialized
face, body, hair, base makeup, clothing and accessory values before any reference
is bound. It returns destinations plus diagnostics. The card's original bytes
remain unchanged. Each destination contains its full property path, unprefixed
catalog property, current category and current source slot.

The scanner currently accepts Custom and Coordinate block version `0.0.0`, face
and body record version `0.0.2`, hair `0.0.4`, base makeup `0.0.0`, clothes
`0.0.1` and accessories `0.0.2`. Older record conversions are not implemented.
Missing fields or array entries are not replaced with constructor defaults;
unknown versions, malformed records and missing catalog-contract mappings
produce diagnostics. Class maps with duplicate fields are also skipped: the
generic native map reader is stricter than the source class formatter's last-key
behavior.

Coordinate data is a MessagePack array of binary records. Each record contains
length-prefixed clothes and accessory maps, one Boolean byte, and a
length-prefixed makeup map. The base game creates seven outfits and loads only
the first seven serialized entries; later entries remain preserved and are not
reported as destinations. Only the source's first two pupil/paint values, first
four hair parts, nine clothes parts, three clothes subparts and four patterns
per clothes part are visited. Each serialized accessory part uses its own
`type`; the scanner permits up to 4,096 accessory parts per outfit, with other
nested arrays limited to 1,024 entries and the generic MessagePack byte/value
limits still applying. Both jacket and sailor subpart properties are emitted
from the same three values, as in the installed source mapping.

A malformed hair record does not suppress a valid face scan. Similarly,
truncated coordinate framing can still report fields from complete preceding
records, with an explicit diagnostic. This describes available source fields,
not proof that the original game's full loader would accept the same malformed
card. Coordinate makeup is preserved without becoming a resolver destination,
even when its enable flag is set. Resolved metadata does not change the rendered
avatar.

Six native destination tests cover nested source values, all clothes mappings,
accessory category selection, coordinate makeup exclusion, seven-outfit bounds,
invalid integer values, missing mappings, unsupported versions and partial
framing. The optional `IKKOKU_MOD_CATALOG_CONTRACT` fixture checks these mappings
against the independently recovered installed-source contract.

## Migration evidence and remaining scope

The source can optionally migrate an explicit reference before direct lookup:

1. It collects migration rules matching the original GUID with case-sensitive
   comparison. Any `StripAll` rule clears the GUID and triggers compatibility
   resolution.
2. It scans rules in order for the saved `Slot` and saved `CategoryNo`, choosing
   the first whose destination GUID has an installed manifest. That changes the
   GUID and slot and immediately returns.
3. Otherwise, the first installed `MigrateAll` destination changes only the GUID.

This is one pass, not recursive migration chaining. Migration metadata uses the
saved category even though subsequent direct lookup uses the current category.
The independent oracle covers this behavior; automatic native migration and
legacy compatibility fallback remain separate, unfinished work. Reporting a
direct match does not mean arbitrary BepInEx or Harmony behavior is supported.

The original byte-array MessagePack deserializer ignores its consumed-byte
count. It therefore accepts extra bytes after an otherwise valid record. The
native adapter intentionally requires exact consumption and rejects null
records, nonbinary entries, malformed typed fields and records exceeding its
bounds: 10,000 records, 1 MiB per record, 64 MiB of nested record data in total and
65,536 UTF-8 bytes per known string field before GUID trimming.
Original card bytes remain preserved even when a resolver record is rejected.

The installed MessagePack `ReadInt32` accepts fixed integers and explicit 8-,
16- and 32-bit integer tokens, with overflow checked. It rejects 64-bit integer
tokens even when their values fit Int32. The native generic MessagePack reader
retains integer values rather than token width, so its typed adapter also accepts
64-bit tokens whose values fit Int32. The source oracle records this small input
acceptance difference explicitly; neither path accepts numeric overflow.

## Reproduction

```sh
.local/reverse/unitypy-venv/bin/python Tools/reverse/analysis/resolver_contract.py
.local/reverse/unitypy-venv/bin/python -m unittest discover \
  -s Tools/reverse -p test_resolver_contract.py -v
```

The ignored `.local/reverse/cards/resolver/contract.json` includes hashes for
the installed Sideloader assembly and eleven recovered source files. Its fixture
index identifies five complete cards: normal Koikatsu data, EC precedence, EC
without `info`, null EC fallback and legacy dictionary replacement. Additional
binary fixtures cover missing defaults, duplicate map keys and unknown fields.

The normal fixture includes an actual face pupil slot of 17 with a saved
category deliberately different from the face property's category, a second
record targeting the same full property, and an actual outfit accessory of type
122 and slot 1080 targeting the imported `enk.acc.bald` sample. These distinguish
correct source semantics from merely looking up the saved record's category or
accepting the last duplicate reference.

The 19 independent Python tests additionally cover all record truncation points,
integer overflow and null fields, strict versus source trailing-byte behavior,
GUID whitespace and case handling, count limits, direct lookup ordering and
migration selection. They are metadata parity tests; they do not establish
visual parity or the original game's missing-mod UI behavior.
